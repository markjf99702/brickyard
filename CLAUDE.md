# Brickyard

A LEGO app: a static site with no build step, served by GitHub Pages at https://brickyard.junkdrawer.works/. Three parts share one catalog: **My sets**, **Build from your box** and **Shelf planner**. The catalog lives in the browser's localStorage under `brickyard.v1`. Nothing about anyone's sets belongs in this repo.

- **Photos of sets, or a list of set numbers, sent in a session here:** follow `skill/brickyard-cataloger/SKILL.md`. Write the batch JSON and the `.brickyard.json` output to the scratchpad, not the repo, and hand over the link the script prints.
- **Tests:** `npm test` (`node test/core.test.cjs` needs nothing; `test/e2e.mjs` needs Playwright). Keep `js/core.js` free of DOM access so the unit test can run it.
- **Formats** (batch, link, backup) are in `skill/brickyard-cataloger/references/brickyard-format.md`. Link prefix `#b1z` / `#b1j` / `#batch=`; changing the format means bumping the prefix and keeping the old one readable. Every kind of link also has a checked form (`#b2z`, `#b2j`, `#l2z`, `#z2z`, `#d2z`) with seven characters on its end worked out from the rest (`linkCheck` in `js/core.js`, `js/shelf-core.js` and `js/build-core.js`; `link_check` in both scripts): they must all work it out the same way, the unit tests compare them, and the unchecked `1` forms must keep opening (Stud Finder still sends them). The page (`cleanSet` in `js/core.js`) and the script (`clean` in `make_brickyard.py`) must clean the same way; the unit test checks they agree.
- **A model request, or "My Brickyard pieces" pasted here:** follow `skill/brickyard-designer/SKILL.md`. Models and their output go to the scratchpad; hand over the link `check_model.py` prints.
- **Build from your box:** the checks live in `js/build-core.js` and `check_model.py` (`check`) and must agree; `test/build.test.cjs` compares them. A new set joins the pool by adding `parts/sets/NUM-1.json` (`{"num", "parts": [[ldraw part, ldraw colour, qty], ...]}`) and its count to `parts/index.json`. A list is the set's inventory from Rebrickable's free downloads (`inventories.csv.gz` and `inventory_parts.csv.gz` at cdn.rebrickable.com/media/downloads/): the latest version, spares included, part numbers turned into LDraw ones (`parts/aliases.json` has the usual ones, 3023 to 3023b) and Rebrickable colour ids into LDraw colour numbers (158 Yellowish Green is LDraw 326, 182 Trans-Orange is 57). `parts/sets/10698-1.json` is exactly that for 10698, 804 pieces against the box's 790 because of the 14 spares; a new list's total should likewise be the box's count plus its spares. Parts the builder can draw are in `parts/shapes.json`. Other numbers for the same piece are in `parts/aliases.json`, beside the shapes; the page (`useAliases`) and the script (`use_aliases`) must read it the same way, and `test/build.test.cjs` compares them. The designer skill carries its own copy of `parts/` in `skill/brickyard-designer/data/`: after any change under `parts/`, run `node tools/copy-skill-data.mjs` (the tests fail until it matches), and the skill then needs uploading to Claude again.
- **Loose pieces:** lots live in the catalog (`loose` in `cleanDoc`/`mergeDocs`, `cleanLot` in `js/core.js`) and arrive as `{"brickyard": 1, "loose": {id, name, box, parts: [[ldraw part, ldraw colour, qty, name?], ...]}}`, by link (`#l1z` / `#l1j`) or file; the same id replaces. `js/build.js` adds ticked lots to the pool (`poolLots`). Which sets and lots count as Your pieces, and how many pieces that is, is `yourPieces` in `js/core.js`, used by `js/build.js` and by the home screen's card: the two must show the same number. `check_model.py --pieces` reads a lot file or pasted "My Brickyard pieces" text. The format is in `brickyard-format.md`. Stud Finder (the tray scanner) is the main sender.
- **Shelf planner:** bookcases live in the catalog (`cases` in `cleanDoc`/`mergeDocs`, `cleanCase` in `js/core.js`); a bookcase there is its frame only, and each set's place on a shelf is kept on its own in `places`, with its own time, so devices merge set by set: `shelves` in `js/core.js` joins the two for the screen and `putShelf` takes a bookcase apart again to save it (a catalog from before, with the sets inside each bookcase, is still read); fitting and sizes links (`#z1z`) are in `js/shelf-core.js`, and `clean_sizes` in `make_brickyard.py` must match `cleanSizes` (`test/shelf.test.cjs` checks). A request for set sizes: follow the sizes section of the cataloger skill.
- **Google Drive sync:** `js/sync.js`, following the junkdrawer.works Drive rules (shared client, `drive.file`, shared `junkdrawer.google` sign-in, never revoke; works only at brickyard.junkdrawer.works). It merges through `mergeDocs` and `app.takeDoc`; models, pool toggles and prefs stay per device. `test/sync.mjs` runs it against `test/fake-google.mjs`. If what syncs changes, update the README and junkdrawer.works/privacy.html.
- **Backups and removed sets:** a backup file carries the catalog, the models and when it was saved; opening one merges, or goes back to it (`restoreDoc` in `js/core.js`). Twins made by two devices adding the same set are folded on a first sync and when a backup or catalog link is opened (`foldTwins`). Kept on each device beside the catalog, not synced: the Recently removed list (`brickyard.removed`, 30 days) and when the last backup was (`brickyard.backup`). `test/core.test.cjs` and `test/e2e.mjs` cover them; don't change `mergeDocs` without them in mind.
- Style: ES5-ish `var`/`function` code in IIFEs, like the other junkdrawer.works apps, except `js/build.js`, an ES module because three.js is; no dependencies beyond the vendored three.js. When the file list changes, bump `CACHE` in `sw.js`. After changing any file in its `SHELL` list, set `FILES` in `sw.js` to the value `test/e2e.mjs` prints: it is a fingerprint of those files, so an installed copy is replaced whole.
